## Sobre el proyecto

**UltromYoutube** es una suite para la automatización de canales faceless de YouTube. Cubre el flujo de generación de contenido: definición de canal (nicho, tono, voz), premisas, prompts de música, thumbnails, estilo visual y animación.

## Archivos clave

- [ultrom-estudio.html](ultrom-estudio.html) — UI actual de la suite (single-file HTML/CSS/JS). Leerlo antes de tocar cualquier parte de la interfaz para entender la estructura, el sistema de pasos (stepper) y los estilos existentes.
- `vol*.txt` (por ejemplo [vol1_channels_extracted.txt](vol1_channels_extracted.txt)) — fuentes de datos con las definiciones de canales: nicho, premisa, tono, mezcla de voz, prompts de música, thumbnail, estilo y animación. Consultarlos para entender el formato y contenido de los datos que consume/produce la suite.
- [render.js](render.js) — pipeline de renderizado de video en etapas via FFmpeg nativo (Ken Burns, subtítulos .ass, mezcla de audio con ducking, mux final). Requerido por `server.js`, usado por `/api/render-video` para todo lo que NO sea 9:16. Ver "Motor de render" más abajo.
- [remotionRender.js](remotionRender.js) — motor de render alternativo para 9:16 vía **Remotion** (React), usando el proyecto hermano `ultron/`. Reusa las etapas de mezcla de audio/mux de `render.js` (no las duplica). Ver "Motor de render" más abajo.
- `ultron/` — proyecto Remotion hermano (Node/TS separado, con su propio `package.json`/`node_modules`) que renderiza video vertical con subtítulos animados palabra por palabra. Documentado en detalle en `ultron/README.md`. También funciona standalone por CLI (`npm run generate -- --channel "..."`), independiente de la integración en `remotionRender.js`.
- `Wan2GP/` — instalación local de WanGP (generación de video con IA vía modelos Wan). Desde 2026-08-21 SÍ está conectada a la app principal (paso 7, ver bullet de `/api/generate-scene-media` más abajo), vía `ultron/scripts/lib/generateBrolls.js` + `ultron/scripts/wan2gp_bridge.py`. Sigue **no verificada end-to-end** (ver `ultron/README.md`, sección Wan2GP): no hubo una instalación real disponible para probarla en vivo, así que el cableado es best-effort — probarla standalone (`ultron/scripts/generate-video.js` con `WAN2GP_ROOT` seteado) antes de confiar en el resultado desde la app web.
- `image-generation-skill/` — clon de [grapeot/image-generation-skill](https://github.com/grapeot/image-generation-skill) (repo Python, `uv`/`pip`, SDK `google-genai`). Integrado como utilidad standalone de generación de imagen con Gemini, **no** cableada al pipeline de escenas (`IMAGE_PROVIDER`/`selectBackground.js`) a menos que se pida explícitamente. Ver sección "Gemini / image-generation-skill" más abajo.

## Cómo correr el proyecto

1. `copy .env.example .env` y completar `LLM_API_KEY` (NVIDIA NIM o FreeLLMAPI) en `.env`.
2. Para locución: abrir la app **Voicebox** (voicebox.sh) — debe quedar corriendo local en `http://127.0.0.1:17493`. No hace falta API key (`TTS_PROVIDER=voicebox` es el default).
3. Para renderizar video (paso 9): tener **ffmpeg** instalado y en el PATH (o `FFMPEG_PATH` en `.env`). Se detecta solo al arrancar el servidor.
4. `node server.js` (o `npm start`) — sirve el proyecto en `http://localhost:3000/`.
5. Abrir `http://localhost:3000/` en el navegador. **No abrir `ultrom-estudio.html` con doble clic** (`file://`): el `fetch` de `channels_data.json` y los pasos que llaman a `/api/generate-script` / `/api/generate-audio` necesitan que se sirva por `http://`.

[server.js](server.js) es un servidor Node sin dependencias externas: sirve los estáticos del proyecto y expone tres rutas proxy (para no exponer ninguna API key en el navegador ni pegarle a Voicebox con CORS desde el front):
- `POST /api/generate-script` — texto/guion, hacia un proveedor de LLM compatible con `/v1/chat/completions` (NVIDIA NIM o FreeLLMAPI). Usada tanto por el paso "Generar guion" como por el resto de funciones de IA de la app (prompts de imagen/animación, SEO, hooks, shorts derivados) vía la función `callClaude()`.
  - `callChatCompletions()` (en `server.js`) orquesta primario → fallback → reintento del primario: 1) intenta el proveedor primario con timeout corto (`LLM_TIMEOUT_MS`, default 18s — mucho más corto que el resto de llamadas externas, que usan 90s); 2) si falla, y hay un fallback configurado (`LLM_FALLBACK_*` en `.env`, pensado para Groq por su latencia sub-segundo), lo prueba; 3) si también falla (o no hay fallback), reintenta el primario una última vez. Nunca deja la request colgada más de ~2-3x `LLM_TIMEOUT_MS`, y el error final junta el detalle de cada intento. Sin `LLM_FALLBACK_API_KEY` configurada el fallback queda deshabilitado — confirmado en pruebas reales que sin él, si NVIDIA está caído, no hay forma de generar guion (el servidor no se cae y responde rápido con el error, pero no hay a dónde más recurrir).
- `POST /api/generate-audio/start` + `GET /api/generate-audio/status?jobId=` + `GET /api/generate-audio/result?jobId=` — locución async con polling: `start` encola la generación en **Voicebox** (`POST /speak`) y devuelve enseguida (no bloquea), el front sondea `status` cada 3s mostrando el tiempo transcurrido, y pide `result` cuando termina. Evita que un solo fetch quede colgado 90-180s+ sin feedback (eso disparaba la sensación de error/timeout). También soporta Fish Audio o NVIDIA NIM como alternativas vía `TTS_PROVIDER` (síncronas, cachean el resultado en memoria bajo un jobId propio); NVIDIA NIM hosted resultó requerir gRPC (no REST) para este modelo, así que ese cliente queda solo de referencia. Queda además `POST /api/generate-audio` (síncrono, bloqueante) como variante simple para integraciones externas. El botón "🔊 Generar Locución" del paso 4 (Guion) usa el flujo async — el resultado se auto-carga como narración en el paso 5 vía `loadBlobAsNarration()`. Es independiente del banner de TTS gratuito ya existente en el paso 5 (Audio), que sigue usando su propio mecanismo basado en StreamElements/Google Translate sin backend.
- `GET /api/voice-profiles` — lista los perfiles de voz configurados en Voicebox (`id`, `name`). El selector de "Perfil de voz" del paso 4 se auto-selecciona si un perfil tiene el mismo nombre que el canal elegido.
- `POST /api/generate-scene-media/start` + `GET /api/generate-scene-media/status?jobId=` — medios de escena en lote (async con polling, mismo patrón que la locución). **Reemplazó al gateway de Grok el 2026-08-21** (ver nota fechada más abajo). Por cada escena: intenta primero un B-roll de **video real con Wan2GP** (`isWan2GpConfigured()`/`generateBroll()` de `ultron/scripts/lib/generateBrolls.js`, subproceso Python vía `wan2gp_bridge.py`) y, si no está configurado o falla para esa escena puntual, cae a una **imagen IA con Pollinations.ai** (`generateImage()` de `ultron/scripts/lib/generateImage.js`, sin API key) — mismo código que ya usaba el pipeline CLI standalone de `ultron` (`generate-video.js`), reusado tal cual en vez de duplicado. Configuración (`WAN2GP_ROOT`, `IMAGE_PROVIDER`, etc.) vive en `ultron/.env`, no en el `.env` raíz — `server.js` lo carga también (`loadDotEnv()`). Cada medio se guarda en `public/assets/scenes/scene_NNN.<ext>` (`.mp4` si salió de Wan2GP, `.jpg`/`.png`/`.webp` si es imagen) y se asigna a `state.media[NNN]` (con su `mediaType`) emparejado por índice de escena/timestamp del turboscript. Botón "🎬 Generar medios de escena (Wan2GP / Pollinations)" en el paso 7, dispara el job, sondea el progreso en vivo y al terminar navega automáticamente al paso 8.
  - **Limitación conocida:** ambos generadores producen siempre vertical 768x1344 (default fijo de `generateImage.js`/`wan2gp_bridge.py`) — no hay forma de pedir otra resolución desde acá todavía. Para 16:9/carrusel el render igual cubre el cuadro (crop en `renderSceneClip`), pero con más recorte que si la fuente ya viniera en ese aspecto.
  - **Wan2GP no verificado end-to-end** (ver `Wan2GP/` más arriba) — sin `WAN2GP_ROOT` configurado, este paso usa directo Pollinations, que sí se probó en vivo (ver nota fechada abajo).
- `POST /api/scenes/upload?index=N` y `POST /api/audio/upload?type=narration|music|sfx&name=` — suben a disco (bytes crudos en el body, sin multipart) los medios que el render necesita pero todavía solo existen como `blob:` en el navegador: escenas subidas a mano en el paso 8 (las generadas por Wan2GP/Pollinations ya están en disco) y el audio actual (narración/música/SFX). El paso 9 los sube solo, justo antes de renderizar.
- `POST /api/render-video/start` + `GET /api/render-video/status?jobId=` — arma el video final **100% en el servidor**, con dos motores posibles (ver "Motor de render" más abajo). El resultado siempre queda en `public/assets/renders/render_<jobId>.mp4`, con el mismo contrato de job (`status`/`stage`/`percent`/`error`/`url`) sin importar cuál corrió — el resto de la app no necesita saberlo.
  - Verificado con pruebas reales (no mockeadas), ambos motores: pipeline completo corriendo de punta a punta, subtítulos inspeccionados visualmente frame por frame (incluido el resaltado palabra por palabra de Remotion), Ken Burns confirmado comparando frames de inicio/fin de una escena, y el ducking de audio confirmado cuantitativamente (7dB de atenuación medida en la música cuando hay narración presente vs. ausente).

## Motor de render (FFmpeg puro vs. Remotion)

Desde 2026-08-21, `/api/render-video/start` elige el motor según `aspectRatio`:

- **9:16 → Remotion** ([remotionRender.js](remotionRender.js)), usando el proyecto hermano `ultron/`. Reemplaza las etapas 1-3 de `render.js` (clips Ken Burns por escena + concat + subtítulos `.ass` quemados) por un único render de React (`VerticalVideo`, ver `ultron/src/`) con subtítulos **animados palabra por palabra** (resaltado amarillo + "pop" de escala, ver `ultron/src/components/Captions.tsx`) — bastante más pulido que el `.ass` estático anterior. Las etapas 4-5 de `render.js` (mezcla de audio narración+música con ducking + mux final) se **reusan tal cual, sin duplicar** (`render.js` las exporta: `buildAudioMix`, `muxFinal`, `newJobDir`, `cleanupJobDir`).
  - Flujo: copia narración + imágenes/videos de escena a `ultron/public/assets/render_jobs/<jobId>/` (Remotion solo puede servir estáticos desde `ultron/public/`, vía `staticFile()`) → arma un `guion.json` (captions armados con `captionsFromSegmentWindows()` de `ultron/scripts/lib/alignTimestamps.js`, reusado tal cual — mismo split proporcional por palabra que ya usaba `buildAssSubtitles()`) → corre `npx remotion render VerticalVideo` como subproceso (cwd=`ultron/`, captura stdout/stderr a diferencia del wrapper propio de ultron que usa `stdio:'inherit'`) → el mp4 resultante (visuales + narración horneada) entra a las etapas 4-5 de siempre. Limpia los assets copiados y el jobDir al terminar (éxito o error).
  - **Limitación real:** la composición de `ultron` está fijada a 1080x1920 @ 30fps (`ultron/src/constants.ts`) — por eso este motor SOLO se usa para 9:16.
  - Progreso durante el render de Remotion: best-effort, parseando el último `NN%` que aparezca en su stdout/stderr (el CLI no documenta un formato estable para consumo programático) — si el patrón no matchea en una versión futura de Remotion, el `%` del job no se mueve durante esa etapa pero el render sigue y termina bien igual.
  - Requiere `ultron/node_modules` instalado (`cd ultron && npm install`) — el servidor lo chequea al arrancar y avisa por consola si falta.
- **Todo lo demás (16:9, etc.) → FFmpeg puro** (`render.js`, sin cambios): 1) un clip silencioso por escena (`zoompan` con upscale previo = Ken Burns en imágenes; recorte/loop a duración exacta en videos; negro si la escena no tiene medio), 2) concat demuxer, 3) subtítulos `.ass` quemados (`buildAssSubtitles()`: una palabra a la vez, mayúsculas, alternando amarillo/rojo, sin resaltado animado), 4) mezcla de audio, 5) mux final. Resolución: 1920x1080.
  - **Gotcha de Windows resuelto:** el filtro `ass=` de ffmpeg rompe con rutas absolutas tipo `C:\...` (el `:` después de la letra de unidad choca con su propio parser interno). La solución fue correr cada proceso de ffmpeg con `cwd` = el directorio temporal del job y pasar solo nombres de archivo sueltos (nunca rutas absolutas) en los argumentos de filtro — evita tener que escapar nada.

## Automatización del pipeline

Al generar la locución (paso 4, Voicebox), además de auto-cargarse como narración en el paso 5, `autoAdvanceAfterLocucion()` encadena automáticamente: confirma el audio (el decodeo con Web Audio API ya certificó que es válido, no hace falta que un humano lo escuche entero) → `generateTurboscript()` → navega al paso 7 → `generateImagePrompts()` → `generateAnimationPrompts()`. **Importante:** esas tres funciones nunca lanzan excepción cuando fallan (capturan su propio error y lo muestran en su UI, pensado para uso manual con alguien mirando la pantalla) — por eso la cadena revisa explícitamente `state.turboscript.length` / `state.imagePrompts` después de cada paso antes de seguir. Sin ese chequeo, un fallo silencioso deja al siguiente paso pegando contra su propio `alert()` de precondición ("Genera el turboscript primero"), que en un flujo 100% automático sin nadie para cerrar el diálogo congela la página entera en silencio (bug real, encontrado y corregido durante el desarrollo).

**Nota sobre NVIDIA NIM:** el modelo default se ajustó primero a `meta/llama-3.1-70b-instruct` (porque `meta/llama-3.1-8b-instruct` quedó DEGRADED del lado de NVIDIA en ese momento) y después a `meta/llama-3.3-70b-instruct` (mismo catálogo NIM, mejor latencia/disponibilidad reportada) — pero en pruebas reales del 2026-08-20 NVIDIA siguió sin responder dentro de 18s ni con el modelo nuevo, dos intentos seguidos. Todas las llamadas salientes del servidor (LLM, TTS síncrono, generación de medios de escena) tienen timeout (`AbortSignal.timeout()` en las llamadas HTTP; el subproceso de Wan2GP usa su propio `--timeout` + el `timeout` de `execFile`) para que un proveedor colgado no cuelgue el servidor entero sin feedback; además hay un `process.on('uncaughtException'/'unhandledRejection', ...)` a nivel proceso que loguea y sigue vivo en vez de tirar el servidor entero (la causa más probable del `NetworkError when attempting to fetch resource` del lado del navegador: el proceso de Node se moría y la siguiente request ni llegaba a conectar).

**Actualización 2026-08-20 (mismo día, más tarde):** se volvió a probar `meta/llama-3.1-8b-instruct` en vivo contra el catálogo NIM real y respondió correctamente en 1-3s (tanto con un prompt suelto como con el prompt estructurado que pide JSON de guion) — el estado DEGRADED documentado arriba ya no aplica, era una condición transitoria del lado de NVIDIA, no permanente. `LLM_MODEL` se cambió a `meta/llama-3.1-8b-instruct` y `LLM_TIMEOUT_MS` se bajó a `5000` (era 18000) en el `.env`. Contraparte observada: al ser un modelo más chico, sigue con menos disciplina la instrucción de "4 a 8 segmentos" del prompt de guion (devolvió 1-3 en las pruebas) y a veces pone las `keywords` en español en vez de en inglés — si hace falta guion más largo o keywords más consistentes, conviene reforzar esas reglas en el prompt (`ultron/scripts/lib/generateScript.js`) antes de volver a un modelo más grande. El fallback a Groq (`LLM_FALLBACK_*`, ver arriba) se deja configurado igual como red de seguridad — sin una `LLM_FALLBACK_API_KEY` real en `.env`, la generación de guion/prompts no tiene forma de recuperarse si NVIDIA se degrada de nuevo (con cualquier modelo).

**Actualización 2026-08-21 (noche):** `LLM_TIMEOUT_MS=5000` resultó demasiado corto para los pedidos más pesados del paso 7 (prompts de imagen/animación para muchas escenas de una sola vez) — probado en vivo contra NVIDIA con un pedido real de 19 escenas: **5388ms**, apenas por encima del timeout, causando el error `nvidia no respondió en 5s` aunque el proveedor no estaba caído (una llamada corta de guion sí responde en <1s). Subido a `LLM_TIMEOUT_MS=20000` en `.env` — confirmado con el mismo pedido de 19 escenas vía `/api/generate-script` real (no simulado): HTTP 200 en ~5s, con margen de sobra. Si en el futuro los prompts en lote crecen más (más escenas, `maxTokens` más alto), conviene volver a medir antes de asumir que el timeout alcanza.

## Multi-usuario (aislamiento por sesión)

**Actualización 2026-08-22:** el servidor está pensado para que varias personas lo usen contra la misma PC al mismo tiempo (caso real: 11 personas en distintas ciudades, ~4 en simultáneo, accediendo vía Tailscale mientras el dueño del proyecto tiene Voicebox abierto). Antes de esta fecha, los archivos de escena/audio se guardaban con nombre fijo (`public/assets/scenes/scene_000.jpg`, `public/assets/audio/narration.mp3`) — dos proyectos generando a la vez se pisaban entre sí sin ningún aviso.

Ahora cada pestaña del navegador genera un `sessionId` propio (`getOrCreateSessionId()`, persistido en `localStorage` bajo `ultrom_session_id`, separado del snapshot de autosave) y lo manda en cada request que toca archivos en disco: `/api/scenes/upload`, `/api/audio/upload`, `/api/generate-scene-media/start` y `/api/render-video/start`. El servidor (`sessionScenesDir()`/`sessionAudioDir()` en `server.js`) guarda todo bajo una subcarpeta por sesión (`public/assets/scenes/<sessionId>/scene_000.jpg`, etc.) — `sanitizeSessionId()` valida el id (solo `[a-zA-Z0-9_-]`, máx 64 chars) y cae a `"default"` si falta o es inválido, para no romper integraciones externas que llamen a la API directo sin mandar `session`. "Descartar y empezar de cero" (`clearAutosave()`) rota el `sessionId` además de borrar el autoguardado, para que un proyecto descartado no comparta carpeta con el siguiente.

Los jobs de generación (`AUDIO_JOBS`/`MEDIA_JOBS`/`RENDER_JOBS`) ya eran seguros para esto sin tocarlos — se identifican por un UUID random propio (`crypto.randomUUID()`), no por nombre fijo, así que nunca colisionaron entre usuarios.

Verificado en vivo (no simulado): dos sesiones distintas subiendo la escena 0 al mismo tiempo con contenido diferente, ambas persisten intactas sin pisarse; y una sesión nueva sin narración propia devuelve el error esperado ("No hay narración subida") en vez de encontrar por accidente la de otra sesión.

**Limitación conocida, no resuelta todavía:** las carpetas por sesión no se limpian solas (a diferencia de los jobs, que sí tienen TTL) — con uso sostenido de 11 personas, `public/assets/scenes/` y `public/assets/audio/` van a acumular carpetas viejas indefinidamente. No es un problema de correctness, solo de disco — si hace falta, conviene un barrido periódico (ej. Task Scheduler) que borre subcarpetas con más de N días sin modificarse.

## Persistencia (autoguardado)

El progreso de la pipeline actual (canal, formato, idea, guion, prompts, prompts de imagen por escena, medios de escenas generados con Wan2GP/Pollinations, metadata, idioma, paso actual e historial de proyectos) se autoguarda en `localStorage` (clave `ultrom_autosave_v1`) cada 5s y antes de cerrar/recargar la pestaña. El audio de narración generado se guarda aparte en IndexedDB (`ultrom_autosave_db`, store `blobs`, clave `narration`) porque no entra cómodo en `localStorage`. Los medios subidos a mano (`state.media`) son `blob:` URLs que mueren al recargar, así que nunca se persisten — pero los medios generados por Wan2GP/Pollinations tienen una URL real servida por el propio servidor (`/public/assets/scenes/...`), así que esos sí sobreviven a una recarga (ver `getPersistableMedia()`). Al cargar la página, `restoreAutosave()` recupera todo automáticamente y muestra un aviso arriba con opción de "Descartar y empezar de cero". Esto es un autoguardado en segundo plano — no reemplaza al historial manual de proyectos (💾 Guardar proyecto actual, paso 2), que sigue siendo la forma de guardar varios proyectos con nombre.

## Actualización 2026-08-24: Gemini / image-generation-skill integrado

Se clonó [grapeot/image-generation-skill](https://github.com/grapeot/image-generation-skill) en `image-generation-skill/` (raíz del proyecto, mismo nivel que `Wan2GP/`) y se instaló con `uv venv` + `uv pip install -e .` dentro de ese mismo directorio (venv propio en `image-generation-skill/.venv`, no toca el resto del proyecto). Es una utilidad **standalone** para generar imágenes con Gemini desde cualquier parte de la app — a diferencia de Wan2GP/Pollinations, no está enganchada al paso 7 (`/api/generate-scene-media`) ni al switch `IMAGE_PROVIDER`.

- [ultron/scripts/lib/generateGeminiImage.js](ultron/scripts/lib/generateGeminiImage.js) — `generateGeminiImage(prompt, options)`, mismo patrón defensivo que `generateBrolls.js`: nunca tira excepción, devuelve `null` + un `console.warn` si algo falla (sin `GEMINI_API_KEY`, si Gemini rechaza el prompt, etc.). Opciones: `outPath` (default `output/gemini_<timestamp>.png`), `seed`, `referenceImagePath`, `aspectRatio`, `size`, `model`.
- [ultron/scripts/gemini_image_bridge.py](ultron/scripts/gemini_image_bridge.py) — subproceso Python que llama al SDK `google-genai` directo (mismo contrato `{"ok":...}` en stdout que `wan2gp_bridge.py`). Corre con el Python de `image-generation-skill/.venv` (autodetectado; override con `GEMINI_SKILL_PYTHON`).
- [scripts/example-gemini-image.js](scripts/example-gemini-image.js) — ejemplo runnable (`node scripts/example-gemini-image.js`) con el prompt "un paisaje futurista con montañas flotantes".
- Config en `ultron/.env` / `ultron/.env.example`: `GEMINI_API_KEY` (o `GOOGLE_API_KEY`), `GEMINI_IMAGE_MODEL` (default `gemini-3.1-flash-image-preview` — el más barato/rápido del catálogo de imagen de Gemini, confirmado en el `.env.example` del repo clonado), `GEMINI_SKILL_ROOT`, `GEMINI_SKILL_PYTHON`.

**Por qué no se usa el CLI `generate-image` del repo clonado directamente:** su función `generate()` (`image-generation-skill/src/image_generation_skill/core.py`, leído verbatim) arma el `GenerateContentConfig` sin `seed=` — no hay forma de pedirle reproducibilidad por ese camino. `gemini_image_bridge.py` llama al mismo SDK (`google-genai`, ya instalado por el repo clonado) replicando esa función pero agregando `--seed` y `--reference`.

**Sobre `seed` (pedido explícito del usuario para consistencia entre generaciones) — límite real, no un bug:** el SDK expone `seed` en `GenerateContentConfig` (confirmado leyendo el código fuente instalado, `google-genai==1.75.0`) pero lo documenta como *best effort* ("the model makes a best effort to provide the same response for repeated requests"), sin garantía pixel a pixel para salida de imagen — a diferencia de motores tipo Stable Diffusion. Se implementó igual (no cuesta nada pasarlo y puede sesgar hacia resultados más parecidos), pero **no depender de él solo** para consistencia visual real. Por eso `generateGeminiImage` también soporta `referenceImagePath` (pasa una imagen previa como parte adicional del request, mismo mecanismo `image_paths` que ya soporta el repo clonado) — es el camino que estos modelos ("nano banana") sí sostienen documentadamente para mantener personaje/estilo entre imágenes.

**Verificado en vivo (2026-08-24), sin mockear:** con una `GEMINI_API_KEY` inválida a propósito, la cadena completa Node → subproceso Python → SDK `google-genai` → HTTP real a `generativelanguage.googleapis.com` se ejecutó de punta a punta y devolvió `400 API_KEY_INVALID` — confirma que la construcción de `Part`/`ImageConfig`/`GenerateContentConfig` (incluido `seed`) es válida para el SDK instalado, y que el manejo de errores no rompe en ningún punto de la cadena (exit code 1 limpio, sin stack trace). **No verificado:** la generación real de una imagen con una key válida — no había ninguna disponible en este entorno al momento de integrar esto.
